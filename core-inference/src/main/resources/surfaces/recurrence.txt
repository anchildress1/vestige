## Surface: Recurrence

Match the entry against retrieved history chunks (provided in the user content block).

What to capture:

- Whether this entry repeats a behavior, vocabulary pattern, or state shift seen in a retrieved historical entry.
- Which retrieved chunk is the closest match.
- Whether the recurrence is exact (same activity + same context) or partial (same activity, different context).

What goes in the schema:

- Populate `recurrence_link` with the chunk reference (`chunk-1`, `chunk-2`, `chunk-3`) of the matched entry, or null when no match.
- Populate `recurrence_kind` with `exact` or `partial` when `recurrence_link` is non-null.
- Do not encode the chunk reference into `tags`. The structured `recurrence_link` field is the only place it belongs; tags must remain short kebab-case tokens per the output schema.
- Use the chunk reference exactly as labeled in the RETRIEVED HISTORY section (`chunk-1`, `chunk-2`, `chunk-3`). Do not use other forms.

Constraints:

- Do not invent a chunk reference. Use only references present in the RETRIEVED HISTORY section.
- Context-only chunks (labeled `context-only`) can inform the reading, but they cannot populate `recurrence_link`.
- Do not infer recurrence from semantic similarity if no retrieved chunk references it. The retrieval layer is the only source of historical context for this surface.
- If the user content contains no retrieved-history block, `recurrence_link` is null. This is normal for early entries.
